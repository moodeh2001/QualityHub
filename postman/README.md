## Manual sequence

1. Start the existing local API/database and check health.
2. Select your authorized dedicated sandbox and inspect the product/variant responses. Update fixture variables to actual IDs with enough available stock; historical IDs are not guaranteed in another sandbox.
3. Run requests in saved folder order. Authentication negative cases clear token state. Successful login precedes Get Current User; rerun successful login before running that protected request independently.
4. Run Create Guest Cart, Get Guest Cart, then Add Product to Cart. Creation clears stale cart_id; cart preflights require private sandbox mode. Repeating Add Product increments quantity and checks exact prior+submitted quantity, line totals, subtotal, shipping, grand total and item count.
5. Review both failed and skipped requests in Postman's UI. A skipped write is incomplete testing, not a passing scenario. Check request-level configuration and environment values before retrying.
6. Keep evidence with its execution date/environment and redact secrets manually before sharing.

The API's guest carts are accessible by ID within the sandbox; the inspected application does not require guest_token authorization. The collection retains its guest-token response assertion. Some catalog/category requests intentionally use public read-only data. Cart writes affect the private sandbox and reserve stock; no automatic teardown deletes records.

Use a Postman runtime supporting pm.execution.skipRequest(). Disable automatic request redirects in Postman settings while handling private credentials. The collection's 500 ms assertion is an inherited project target, not an official API performance specification.

The five Product Variants checks remain dynamic, deriving product ID from the URL. No assertions were removed to make this collection manual-only. No fresh manual Postman run was performed during this scope change; the previous owner's observations remain historical.
